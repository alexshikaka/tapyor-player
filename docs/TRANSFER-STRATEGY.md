# Стратегия передачи проекта другой модели

Цель: в любой момент — хоть через месяц, хоть с другой моделью (Claude, Opus, я) — поднять весь контекст проекта **из GitHub**, а не из чьей-то памяти. Переписка, решения, ошибки и проверки должны быть версионированы вместе с кодом.

Три принципа:

1. **Репозиторий — источник правды.** Всё, что нужно для входа, лежит в `docs/`; чат — доказательство, а не хранилище.
2. **Документы пишутся по ходу работы, а не в конце.** HANDOFF и TODO обновляются каждую сессию; решения и ошибки — в момент, когда они появились.
3. **Релиз = снимок.** На каждый релиз — папка `docs/releases/vX.Y.Z/` с обзором, решениями, ошибками, проверками и ссылкой на полную переписку в ассетах GitHub.

---

## 1. Слои документации

### Слой A. Живые документы (обновляются в каждой сессии)

| Файл | Что внутри | Когда обновлять |
|---|---|---|
| `docs/HANDOFF.md` | Текущее состояние, что сделано, что дальше, карта кода | В конце каждой сессии |
| `TODO.md` | Хронология: что, почему, какими замерами проверено | После каждой правки |
| `docs/DEV.md` | **Как запустить на ПК владельца**: команды, ловушки, что проверено и когда | При каждом изменении способа запуска |
| `docs/DECISIONS.md` | Журнал решений (ADR): контекст → варианты → выбрали → почему → последствия | Когда решение меняет архитектуру/UX |
| `docs/ERRORS.md` | Грабли: симптом → причина → лечение → как не повторить | Сразу после того, как поймали |
| `docs/CHECKS.md` | Чек-лист приёмки для владельца (по версиям) | Перед релизом |
| `docs/SKINS.md` | Контракт оболочек и правила «только покраска» | При изменении скинов |

### Слой B. Доказательства сессии

| Что | Где | Размер |
|---|---|---|
| Краткий дайджест переписки (запрос → суть ответа) | `history/COMPACT.md` в репозитории | ~100 КБ за релиз |
| Подробный дайджест | ассет релиза `history-DIGEST-vX.zip` | ~200–300 КБ |
| Полная стенограмма | ассет релиза `history-FULL-vX.zip` | 1–3 МБ (zip) |
| Скриншоты проверок | `docs/shots/vX.Y.Z/*.png` (лёгкие) или ассет `shots-vX.zip` | 0,5–5 МБ |

В репозиторий кладём только текст и небольшие PNG. Крупные выгрузки — **в ассеты GitHub Release**, чтобы не раздувать git.

### Слой C. Снимок релиза

```
docs/releases/
  INDEX.md                      # список версий: ссылка, дата, статус, 1 строка о чём
  v0.19.0/
    README.md                   # вход: что за версия, что читать в каком порядке
    CHANGES.md                  # что изменилось для владельца (без жаргона)
    DECISIONS.md                # решения именно этой версии
    ERRORS.md                   # что ломалось и как починили
    VERIFICATION.md             # как проверяли: команды, замеры, скриншоты
    SESSION.md                  # дайджест переписки + ссылки на ассеты
    MANIFEST.json               # commit, tag, дата, версия, хеши, список файлов
    docs/                       # копии HANDOFF/DEV/CHECKS на момент релиза
```

`docs/releases/INDEX.md` — единственная точка входа для новой модели: «последняя версия — v0.19.0, читай `v0.19.0/README.md`, затем `docs/HANDOFF.md`».

## 2. Как это работает в процессе

1. **Во время работы** я обновляю `TODO.md` (каждая правка), `HANDOFF.md` (в конце сессии), `DECISIONS.md`/`ERRORS.md` (по факту), `DEV.md` (если менялся запуск).
2. **Перед релизом** запускается `npm run review:prepare -- 0.19.1`:
   - собирает `docs/releases/v0.19.1/` из живых документов и `git log`;
   - выгружает переписку из DSH-журнала в `history/COMPACT.md`;
   - считает хеши и пишет `MANIFEST.json`;
   - упаковывает большие выгрузки в zip для ассетов.
3. **При публикации** (только по команде владельца): коммит `docs/releases/v0.19.1`, тег `v0.19.1`, в GitHub Release прикрепляются zip-архивы истории и скриншотов, в описании — ссылка на `docs/releases/v0.19.1/README.md`.
4. **При входе новой модели** достаточно дать ссылку на репозиторий и фразу: «начни с `docs/releases/INDEX.md`, потом `docs/HANDOFF.md`, `docs/DEV.md`, `docs/DECISIONS.md`».

## 3. Где будет отражено «как запустить программу у меня на ПК»

Это не разовое знание, а **канонический документ + доказательство**:

| Место | Что именно |
|---|---|
| `docs/DEV.md` | Раздел «Где лежит проект и как запустить» + «Три ловушки» (Electron не ставится через npm, `ELECTRON_RUN_AS_NODE`, права папки). Каждый шаг с точной командой и датой последней проверки. |
| `docs/HANDOFF.md` | Ссылка «как запустить — см. `docs/DEV.md`» в разделе состояния. |
| `docs/releases/vX/DEV.md` | Копия на момент релиза: если завтра способ изменится, видно, как запускали именно эту версию. |
| `docs/releases/vX/VERIFICATION.md` | Строка вида «запуск из исходников проверен 23.10.2026 на ПК владельца, команда …, результат …». |
| `docs/ERRORS.md` | Если запуск ломался — симптом/причина/лечение. |
| `history/…` | Как мы к этому пришли (сырые доказательства), для поиска. |

Правило: **инструкция живёт в `DEV.md`, а не в чате**. Чат — источник, из которого инструкция родилась; если инструкции нет в `DEV.md`, значит её не существует для следующей модели.

## 5. Правила гигиены

- Никаких секретов: токены, `settings.json`, cookies, ключи — не попадают в репозиторий и в выгрузки (скрипт выгрузки фильтрует по шаблонам).
- Скриншоты — только окно приложения, без личных данных.
- Один релиз — одна папка; не редактировать старые снимки задним числом (история важнее красоты).
- В `MANIFEST.json` — хеши файлов снимка, чтобы проверять целостность.
- Полные стенограммы — только ассеты; в репозитории — дайджест, чтобы клон оставался лёгким.
- Если решение отменено — не удалять, а помечать в `DECISIONS.md` как «отменено, причина».

## 6. Прошлые версии

Снимки A появляются только с 0.19.1 — раньше их просто не было. Для старых версий действует архив `docs/releases/ARCHIVE.md` с тремя уровнями полноты:

- **A** — полный снимок (папка версии со всеми файлами);
- **B** — обзор: README + всё, что подтверждается TODO, git-тегом и текстом релиза;
- **C** — только строка в таблице со ссылкой на источник.

Правило: **не выдумывать задним числом**. Если по версии нет записей, ставится C и указывается, где искать (TODO, HANDOFF, тег, старый архив 22.10). Если мы снова трогаем старую версию — её повышают до B, добавляя папку с тем, что реально известно.

Git-теги `v0.17.1`, `v0.18.0`, `v0.19.0` — единственные машинные якоря прошлого; вся более ранняя история существует только в документах, потому что git-история начинается с 0.17.1.
