# План переработки системы скинов

Документ — разбор того, почему Scorched Earth и Winamp «поехали», и какой подход предлагается вместо нынешнего. Ничего из этого ещё не сделано в коде: это проект.

---

## 1. Почему текущий подход сломался

1. **Один монолитный CSS.** Все оболочки живут в `src/index.html` (7 500 строк). Правила оболочек конкурируют с базовыми через `!important`, и предсказать итоговый каскад невозможно.
2. **Скины меняли раскладку.** Чтобы «быть как Winamp», правила трогали `margin`, `padding-bottom`, `gap`, `position` у `main` и панелей. Любое изменение размера окна превращалось в наложение зон.
3. **Декор вставлялся в DOM.** `SKIN_DECOR` добавлял элементы прямо в `footer` и `.queue-col`. Вставленный блок занимал место в потоке и раздвигал раскладку — отсюда «всё наезжает».
4. **Нет проверки геометрии.** Аудит проверял скругления, шрифт и контраст, но не перекрытия, не переполнения и не обрезку текста. Ошибка видна была только глазами.
5. **Нет визуальных эталонов.** Не было скриншотов «как должно быть», поэтому регрессии ловились вручную.

## 2. Что предлагается: контракт вместо CSS-войны

### 2.1. Скин = данные + файл оформления

```
skins/
  dos/
    skin.json        // манифест
    skin.css         // оформление (только paint)
  crt/…
  retro/…
  _template/         // шаблон для новой оболочки
```

`schema.json` (или JS-валидатор в `tests/`) проверяет манифест:

```json
{
  "id": "winamp",
  "name": "Winamp",
  "pixel": false,
  "font": { "ui": "Tahoma", "mono": "Consolas" },
  "geometry": { "radius": { "panel": 0, "card": 0, "control": 0 }, "border": 1, "bevel": true },
  "schemes": [
    { "id": "base", "name": "База 2.x", "desc": "…", "core": { "bg": "#232323", "panel": "…", "surface": "…", "line": "…", "text": "…", "accent": "…", "button": "…" } }
  ]
}
```

Правила для `skin.css`:

- **разрешено**: цвета, фоны, тени, границы, радиусы, шрифты, `filter`, `background-image`, `::before/::after` у своих компонентов;
- **запрещено**: `padding`, `margin`, `width`, `height`, `position`, `display`, `flex`, `grid`, `gap`, `inset`, `transform` — всё, что двигает чужие элементы;
- селекторы только по компонентам из списка (`.card`, `.queue-col`, `.pbtn`, `.row`, …), не по «случайным» вложенным классам;
- никаких `!important`: файл скина подключается **после** базового и выигрывает по порядку.

Валидатор `tests/skins/lint.js` ищет запрещённые свойства в `skins/*/skin.css` и падает на `!important`.

### 2.2. Раскладка — ответственность приложения, а не скина

Вместо того чтобы скин двигал панели, вводим **три режима раскладки**, которые реализует приложение:

| Режим | Как выглядит | Кто использует |
|---|---|---|
| `default` | левая колонка + очередь + подвал | DOS, CRT, ретро |
| `compact` | очередь уезжает под контент, узкие отступы | узкие окна, будущее |
| `frame` | скин рисует «рамку окна», контент внутри слота | Winamp-подобные |

Скин указывает `"layout": "frame"` в манифесте, приложение само раскладывает зоны. Скин не может «сломать» сетку.

### 2.3. Слоты вместо вставки элементов

В разметке появляются слоты:

```html
<div class="skin-slot" data-slot="bg"></div>      <!-- фон/декор, pointer-events:none -->
<div class="skin-slot" data-slot="chrome-top"></div>
<div class="skin-slot" data-slot="chrome-bottom"></div>
```

Слоты:

- не участвуют в раскладке (`position:absolute`, `inset:0`, `pointer-events:none`, `contain:strict`, `overflow:hidden` у контейнера);
- заполняются **только CSS-псевдоэлементами** скина, без DOM-вставок;
- если скину нужен «настоящий» элемент (LCD, спектр), он объявляется в манифесте (`slots: { "chrome-bottom": "lcd" }`), и приложение вставляет его в слот как **абсолютный** блок с фиксированной высотой из токенов.

Итог: декор физически не может раздвинуть интерфейс.

### 2.4. Токены вместо десятков переменных

Скин задаёт только:

```
--bg0 --bg1 --bg2 --ln --tx --tx2 --accent --button --radius-*
```

Остальные производные (тени, ховеры, вторичный текст, рамки, «фаски») считает приложение из ядра. Это уже частично сделано в `skinVarsFromCore` — надо довести до конца и запретить скинам объявлять производные вручную.

### 2.5. Обязательные проверки (гейты)

1. **`audit:geometry`** — для каждой оболочки на ширинах 980 / 1280 / 1600 и высотах 640 / 800 / 1000:
   - ни один элемент не выходит за `.app-shell`;
   - нет пересечений прямоугольников у зон верхнего уровня (`header`, `main`, `footer`, `.queue-col`);
   - текст ключевых подписей не обрезан (`scrollWidth ≤ clientWidth + 1`);
   - минимальный размер кликабельных элементов ≥ 24×24.
2. **`audit:visual`** — скриншоты 5 вкладок × 3 размера для каждой оболочки; сравнение с эталоном в `tests/skins/baselines/<skin>/` с порогом (например, 0.3 % пикселей).
3. **`audit:paint`** (уже есть) — скругления, шрифт, контраст схем.

Гейты запускаются в одном прогоне `npm run audit:skins`, результат — HTML-отчёт со скриншотами.

### 2.6. Процесс добавления новой оболочки

1. Пользователь присылает референсы (скриншоты 1:1, желательно несколько экранов).
2. Снимаем палитру и метрики (шрифт, размеры, радиусы) — вручную или скриптом.
3. Пишем `skin.json` + `skin.css` (только paint), запускаем `lint`.
4. Добавляем схемы, прогоняем `audit:paint` + `audit:geometry`.
5. Снимаем эталоны `audit:visual`, смотрим глазами, прикладываем скриншоты в ответ.
6. Только после зелёных гейтов — в коммит.

## 3. Порядок работ

| Шаг | Что делаем | Риск |
|---|---|---|
| 1 | Вынести CSS трёх оболочек в `skins/*/skin.css`, проверить, что вид не изменился (визуальные эталоны до/после) | средний: механическая работа |
| 2 | Добавить `lint` (запрет layout-свойств и `!important`) | низкий |
| 3 | Реализовать `audit:geometry` и прогнать на текущих оболочках | низкий |
| 4 | Добавить слоты и ограничить декор псевдоэлементами | средний |
| 5 | Ввести `layout` в манифест (`default`/`compact`/`frame`) | средний |
| 6 | Сделать `audit:visual` с эталонами | средний |
| 7 | Новые оболочки — только по процессу из §2.6 | низкий |

Пункты 1–3 можно сделать без изменения внешнего вида — это фундамент, который не ломает текущие скины.

---

## 4. Что нужно от владельца

- референсы новых оболочек: скриншоты 1:1 (лучше 2–3 экрана и «попап/меню», если есть);
- какие элементы интерфейса трогать нельзя (например, размеры кнопок плеера);
- целевые размеры окна: 1280×800 — основной? нужно ли 980 px и ниже?
